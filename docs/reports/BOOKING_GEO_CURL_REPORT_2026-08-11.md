## 1 · The defect

### A malformed UUID in a path parameter returns 500 instead of 400

**Severity: moderate. Pre-existing, and not confined to these two modules.**

```
GET /geo/services/not-a-uuid/areas          -> 500
GET /catalog/services/not-a-uuid            -> 500
GET /catalog/categories/not-a-uuid/services -> 500
GET /bookings/not-a-uuid                    -> 500
```

Server-side:

```
ERROR [AllExceptionsFilter] GET /api/v1/catalog/services/not-a-uuid -> 500
PrismaClientKnownRequestError:
Invalid `this.prisma.service.findUnique()` invocation
```

**What is happening.** A `:id` path parameter is passed straight to Prisma. When
it is not a UUID, Postgres rejects the cast, Prisma throws, and the global
filter — correctly refusing to leak internals — turns it into a generic
`Internal server error`.

**Why it matters.** A client's malformed request is being reported as a server
fault. Three consequences:

1. **It is the wrong answer.** The client sent a bad id; that is a 400.
2. **It poisons error monitoring.** Every scraped id, stale bookmark and typo'd
   deep link becomes a 5xx. Real incidents get buried in noise generated by
   ordinary client mistakes.
3. **It is a free liveness probe.** An unauthenticated caller can distinguish
   "reached the database" from "rejected at the edge" on any `:id` route.

**Scope.** Confirmed on modules **3, 4 and 13**. This is not a geo or booking
bug — it is every route that takes an id in the path and does not validate it,
and there are ~69 such call sites.

**Behaviour is correct once the id is well-formed**, which is what localises the
cause precisely:

```
GET /catalog/services/00000000-0000-4000-0000-0000000000ff  -> 404   ✅
```

**Fix.** One `ParseUUIDPipe` applied globally to `:id` params, or a small
`@UuidParam()` decorator wrapping it. Roughly an hour including specs, and it
closes the class rather than the three instances found here.

**Not fixed in this pass** — it reaches beyond both modules under test and into
module 3, so it belongs in its own change with its own commit.

## 2 · What the geo module got right

### Half-open bounds hold at the seam — verified against real SQL

The load-bearing detail of the rectangle model (#42), and the one most likely
to be broken by a well-meaning edit:

```
lat 22.714    (the shared seam)  -> Vijay Nagar   the UPPER cell
lat 22.71399  (a hair below)     -> Palasia       the LOWER cell
lng 75.858    (the shared seam)  -> Vijay Nagar   the EASTERN cell
lng 75.85799  (a hair west)      -> Rajwada       the WESTERN cell
```

Exactly one cell claims each boundary pin. Not both, not neither.

### Coordinate validation refuses rather than guessing

`lat=abc`, `lat=999`, `lng=999`, a missing `lat`, and no coordinates at all are
all **400**. None of them silently resolves to "we do not serve you", which is
the failure mode that would tell a real customer the wrong thing about our
coverage. `lat=-90&lng=-180` is accepted — the extreme is legal, not an error.

### The client never names its own area

```
GET /geo/serviceability?lat=22.69&lng=75.83&areaId=<Vijay Nagar>  -> 400
POST /bookings  { ..., "areaId": "<Rau>" }                        -> 400
POST /customers/me/addresses  { ..., "areaId": "..." }            -> 400
```

`forbidNonWhitelisted` rejects the smuggled field outright on all three
surfaces. A client that could name its own area could book a service where it is
not offered.

### The two unavailability answers stay distinct

```
Bhopal pin        -> LOCATION_NOT_SERVICEABLE      area: null
Rau + deep clean  -> SERVICE_NOT_AVAILABLE_IN_AREA area: "Rau"
```

"We do not operate here" and "we operate here but not for that" are different
screens, and the second still names the area — because we _do_ serve that
customer, just not for that job.

### The catalogue flags rather than hides

Rau returns **8 services, same as Vijay Nagar**, with the deep clean marked
unavailable. An out-of-coverage pin returns all 8 with everything unavailable
rather than an error — the customer can still browse. This is what stops a
thinly-mapped area from looking like an empty product.

### The admin surface enforces its own rules

- Unauthenticated: **401** on list, grid generation and availability
- Customer token: **403** — authenticated but not entitled
- **Staffing gate fires:** activating a service in an unstaffed area is **409**
  `AREA_NOT_STAFFED_FOR_SERVICE` (#46)
- **Switching a service off is never blocked** — 201 even when unstaffed, so an
  area that lost its last Pro can still be corrected
- Regenerating a grid over a mapped city: **409**
- Inverted and zero-height rectangles: **400**
- Duplicate area name in one city: **409**
- **`/overlaps` is empty**, confirming a generated grid genuinely tiles

## 3 · What the booking module got right

### Price tampering is closed

```
POST /bookings { ..., "flatPrice": 1 }     -> 400
POST /bookings { ..., "totalAmount": 1 }   -> 400
```

The US-7.1 vector. Price is not an input; it is read from the catalogue and
frozen server-side, and an attempt to supply one is rejected rather than
ignored.

### The payment-mode fork behaves

A cash booking goes straight to **`assigning`** — it never passes through
`awaiting_payment` (#20). An online booking on a deployment with no Razorpay
credentials returns a clean **501** rather than half-creating a booking that
would sit unpayable forever.

### Ownership leaks nothing

```
another customer's booking  -> 404   (never 403)
a booking that never existed -> 404
```

Both are indistinguishable, so the API cannot be used to enumerate booking ids.

### Validation is strict, and errors carry codes

Unknown fields, a missing `addressId`, a malformed `serviceId`, an unknown
service (404), a malformed slot time, and an unknown payment mode are all
rejected. Domain refusals carry machine-readable codes —
`BOOKING_TYPE_UNSUPPORTED`, `BOOKING_NOT_TRACKABLE` — so a frontend can branch
without string-matching prose.

### Tracking is withheld when it would mislead

`GET /bookings/:id/tracking` on an `assigning` booking is **409
BOOKING_NOT_TRACKABLE**, not an empty map. A pin before anyone is on the way
would be worse than no pin. `etaMinutes` stays null throughout — the system
still refuses to publish a number derived from a crow-flight guess.

### The area gate is dormant, exactly as designed

A deep clean booked in **Rau — where that service is switched off** —
**succeeds** (201) and records the area. That is #43 working: the gate resolves
and records but does not reject until a city is explicitly switched on. Had this
returned 409, the gate would have been live before anyone intended it.

## 4 · Findings that are not defects, but you should know

### Bookings cannot be created without a reverse geocoder

`POST /customers/me/addresses` returns **503 "Reverse geocoding is not
configured"** when `NOMINATIM_USER_AGENT` is unset — and it is unset in
`.env.local`. No address means no booking, so **the entire booking module is
gated on an external service being configured**, with no fallback that lets an
operator enter a known-good address by hand.

Worth deciding deliberately: is that acceptable for production, where Nominatim
being down would stop all new addresses?

### The geocoder is globally rate-limited to 1 request/second

A Redis lock enforces Nominatim's public-usage policy across all instances.
Correct and deliberate — but it means **concurrent signups serialise on address
creation**, and the second caller gets a 503 rather than queuing. At launch
scale this is fine; it is a known ceiling worth remembering.

### OTP requests are limited to 5/hour per number

Verified live (429). Correct, and worth noting for anyone scripting against
this: the suite salts phone numbers per run for exactly this reason.

### An unknown service id returns 200 with an empty list

`GET /geo/services/<well-formed-but-unknown>/areas` returns `200 []`, which is
indistinguishable from a real service that is live nowhere. Defensible — the
question "where is this available" has the answer "nowhere" either way — but
worth a deliberate call rather than an accident.

## 5 · Fixture work done to make this runnable

- **`test/manual/nominatim-test-server.mjs`** gained three fixtures — pins in
  the seeded Vijay Nagar and Rau cells, and one in Bhopal (a seeded, active city
  with **no areas drawn**, which is the state every new city starts in). Without
  these, no address could be created inside the seeded grid and the area gate
  could not be exercised at all.

- **Phone numbers are salted per run.** Indian mobiles are exactly 10 digits, so
  only four salt digits fit — the suite derives them from the clock.

- **OTP code extraction is anchored.** A bare `grep -oE '[0-9]{6}'` over the log
  line also matches six-digit runs _inside the request UUID_, producing two
  codes, an invalid JSON body, and a login that fails only on the refs that
  happen to contain one. This cost several runs to diagnose and is called out in
  the script so nobody reintroduces it.

## 6 · Recommendation

**One fix, one decision.**

1. **Fix the UUID 500** with a global `ParseUUIDPipe` on `:id` params. It is the
   only defect found, it spans at least three modules, and it converts a class
   of ordinary client mistakes from 5xx noise into correct 400s.

2. **Decide on the geocoder dependency.** Today, an external service being
   unconfigured or down blocks every new address and therefore every new
   booking. That may be an acceptable launch risk — but it should be a decision
   with a fallback attached, not something discovered during an outage.

Everything else in both modules behaved correctly under every edge case thrown
at it, including the ones most likely to be broken silently: the seam
resolution, the price-tampering vector, the ownership 404, and the deliberately
dormant area gate.
